# 内容巡检流程

这份文档是一份**可执行的操作手册**，不是理念说明。

它规定了「让图谱跟上 AI 行业」这件事每次具体做什么：扫哪些源、按什么标准判断、产出成什么样、放到哪里。第 3 节是任务正文，可以原样粘进一个定期任务（autopilot）直接跑。

**巡检只产出建议，不改内容。** 每次巡检的结果是一份「建议新增 / 建议更新」清单，变成 issue 等人消化。内容改动一律走 PR——理由见第 6 节。

## 1. 为什么需要它

图谱有两种死法，巡检要同时防住：

- **腐烂**：新概念铺天盖地，图谱停在 2026 年 9 月。新人查不到「MCP 是什么」，就不再用它。
- **膨胀**：什么都往里塞，节点从 54 涨到 400，每个都只有一句话，图变成一张糊墙纸。

所以巡检的核心不是「找新东西」，是**筛**。一份只列了 3 条、但条条都该进的清单，比一份列了 40 条的更有价值。

## 2. 输入来源

按信噪比从高到低。**至少覆盖 A、B 两类**，C 类是补充。

### A. 一手发布（最高信噪比）

- 模型与能力的官方发布：Anthropic、OpenAI、Google DeepMind、Meta AI、Mistral、DeepSeek、Qwen 的官方博客与发布说明
- 关键工程团队的博客：Hugging Face、vLLM、SGLang、LangChain / LlamaIndex 的 changelog 与 release notes

这类源里，**发布说明比营销博客有用**——营销文讲「我们多强」，发布说明讲「我们引入了什么机制」，后者才是能进图谱的东西。

### B. 论文与研究动态

- arXiv `cs.CL` / `cs.LG` 近两周的新投稿标题与摘要
- Hugging Face Daily Papers
- 顶会（NeurIPS / ICML / ICLR / ACL）的接收列表

不需要读全文。**看标题和摘要就够了**——判断「这个概念要不要进图谱」几乎从来看不出一篇论文的细节。

### C. 行业与社区

- 主流技术媒体、工程周报、高 signal 的技术讨论区

C 类**只用来发现线索**，不用来形成结论。看到什么新词，回到 A 或 B 去找一手来源；找不到一手来源的，按噪音处理。

### 扫描窗口

距上次巡检以来新出现的东西。首次巡检或间隔超过 60 天时，看最近 60 天。

## 3. 每次执行的任务

这一节是 autopilot 的任务正文。照着做，产出在第 4 节。

### 步骤 1：拿到「图谱现在有什么」

先去重，再找新的。否则每轮都会把同一批候选重新提一遍。

```bash
git clone <repo> && cd ai-knowledge-graph
node build/index.js --quiet

# 现有全部节点 id
node -e "console.log(JSON.parse(require('node:fs').readFileSync('web/public/graph.json','utf8')).nodes.map((n) => n.id).sort().join('\n'))"

# 现有全部路径 id
node -e "console.log(JSON.parse(require('node:fs').readFileSync('web/public/paths.json','utf8')).paths.map((p) => p.id).join('\n'))"
```

还要看**上一轮巡检提过什么**，避免重复提案：

```bash
multica issue list --project 92b403a4-119a-439d-a147-0f1d8b5e25a8 --output json
```

标题形如 `内容巡检 <日期>：...` 的 issue 就是历史巡检，把它们提到的候选记下来——**已经在上一轮被否决的，这一轮除非有新证据，否则不要再提**。

### 步骤 2：扫源

按第 2 节的 A、B、C 顺序扫。扫的时候只记「候选」，不判断——判断统一放到步骤 3，免得边看边下结论。

### 步骤 3：逐个过筛

对每个候选，按顺序回答下面的问题。**任何一问答不上，就归到「不建议收录」**，并写清卡在哪一问答不上。

**第一关：它是不是一个概念，而不是一个产品功能？**

图谱收的是「注意力机制」，不是「某个模型的 128K 上下文」。一个功能要能进图谱，得先抽象成概念。

> 反例：`Claude 的 Artifacts 功能` → 这是功能
> 正例：`模型上下文协议（MCP）` → 这是概念，多个产品都在实现它

**第二关：业界是不是已经开始用同一个名字叫它？**

看两三个独立来源是否用同一个词。只有一个来源在用的名字，是在造词，不是在命名。**这一关最常拦住人**——很多看起来很热的东西，三个月后连名字都留不下来。

**第三关：一个 LLM 应用开发者，会不会因为不懂它而在未来 12 个月里做错决定？**

这是整份文档里唯一真正重要的标准。

- ✅ 会——不知道某个机制的存在，就会选错架构、算错成本、踩到已知的坑
- ❌ 不会——知道它很好，但不知道也不影响他把东西做出来

反过来说：**如果不懂它不影响你做决定，那它是资讯，不是知识。** 资讯不该进这张图。

**第四关：能不能说清它挂在谁下面？**

必须能写出一到三个**已存在**的前置节点。说不清，说明这个概念在你的理解里还没成形——**这一关是硬约束，答不上来就不提**。

顺带这一关会暴露另一件事：如果一个候选需要四五个前置才能挂上去，通常说明它自己太大了，应该拆成两个候选。

**第五关：它是一年后还重要，还是这周的热点？**

区分「范式」和「新闻」。榜单分数、版本号、融资、人事变动、公司战略，全是新闻。

**关于「换个名字的同一个东西」**：如果新词指的是图谱里已经有的概念，那它是**建议更新**，不是建议新增——正确的动作是给已有节点补别名、补充新进展，而不是新建一个重复节点。

### 步骤 4：对「已有节点」做一遍体检

新增之外，还要看已有的 54 个节点有没有过期。重点查：

- **事实过期**：节点里写的数字、能力边界、代表模型已经过时（比如某个「最新进展」停留在两年前）
- **来源失效**：`sources` 里的链接打不开
- **层级错位**：L1 里混进了术语，或者 L2 的类比已经不成立
- **依赖漂移**：新节点加进来之后，某个老节点的 `prerequisites` 应该跟着调整

抽查即可，不必逐个过。优先查 `deployment`、`agents`、`evaluation` 这三个领域——它们的事实半衰期最短。

### 步骤 5：写产出

按第 4 节的格式写成 issue。

## 4. 产出物格式

**产出到哪里**：在本工作区的「AI 知识图谱」项目（project id `92b403a4-119a-439d-a147-0f1d8b5e25a8`）下**新建一个 issue**。

autopilot 用 `create_issue` 模式时，issue 会自动创建；正文按下面的模板写。手工跑巡检时对应：

```bash
multica issue create \
  --title "内容巡检 2026-10-06：建议新增 3 / 建议更新 2" \
  --description-file ./patrol-report.md \
  --project 92b403a4-119a-439d-a147-0f1d8b5e25a8 \
  --output json
```

**标题格式**：`内容巡检 <YYYY-MM-DD>：建议新增 N / 建议更新 M`。N 和 M 都是 0 时，标题写成 `内容巡检 <YYYY-MM-DD>：本轮无需变更`，并且**照常建 issue**——「这一轮查过了，没有要改的」本身就是要交付的信息，不然没人知道巡检还在不在跑。

用 autopilot 跑时，`--issue-title-template "内容巡检 {{date}}"` 会先把标题定成日期那一版，**再由这一轮的 run 把计数补进标题**（模板只支持 `{{date}}`，算不出 N 和 M）。补标题这件事要写进任务正文，否则 issue 列表上就只剩日期，看不出哪轮有东西。

**正文模板**：

```markdown
本轮扫描窗口：<起> ~ <止>；扫描源：A（官方发布）、B（arXiv cs.CL/cs.LG、HF Daily Papers）

## 建议新增节点

| 建议 id | 标题 | 领域 | 前置 | L1 草稿 | 依据 | 置信度 |
|---|---|---|---|---|---|---|
| prompt-caching | 提示缓存 | deployment | prompt-engineering | 把每次都要重复发的那段话存在服务商那边，下次直接跳过，省钱也省时间。 | Anthropic 官方文档、OpenAI / Google 均已有对应实现 | 高 |

（没有就写「无」。**一行一个候选，不要合并**——消化的人要能单独勾选。）

### 每条的理由

**prompt-caching** —— 为什么值得进图谱（一句话说清「不懂它会做错什么决定」）；
为什么挂在 `prompt-engineering` 下面而不是别处。置信度的判断依据：
高 = 多个独立一手来源 + 命名已稳定；中 = 单一来源或命名还在摇摆；低 = 苗头不错但还不确定。

## 建议更新节点

| 节点 id | 现状问题 | 建议改什么 | 依据 |
|---|---|---|---|
| model-quantization | L3 里的代表方法停留在 2024 年 | 补充新出现的量化方案 | <来源> |

## 建议废弃 / 合并

（可选。只有在某个节点已经明确被新节点取代时才提，并说明为什么不是「改」而是「删」。）

## 本轮扫过但建议不收录

| 候选 | 不收录的原因（卡在第几关） |
|---|---|
| <某个热门话题> | 第二关：只有单一来源在用这个名字，命名未稳定 |

（**这一节不要省。** 它让下一轮巡检不用把同样的候选重新判一遍，
也让读的人能校准筛选标准是不是太松或太紧。宁可多写几条。）
```

**清单规模**：建议新增控制在 **5 条以内**。超过 5 条说明筛得太松，回过头去把置信度「低」的砍掉。

## 5. 挂成定期任务

巡检本身不绑定任何调度——是否启用、多久跑一次，由工作区决定。要启用时：

```bash
# 1. 建 autopilot：把第 3 节的正文作为任务描述
multica autopilot create \
  --title "AI 知识图谱内容巡检" \
  --description "<把第 3 节「每次执行的任务」全文粘进来>" \
  --agent <agent-id> \
  --mode create_issue \
  --project 92b403a4-119a-439d-a147-0f1d8b5e25a8 \
  --issue-title-template "内容巡检 {{date}}" \
  --output json

# 2. 加一个每周一上午的调度（注意 --timezone，不加按 UTC 跑）
multica autopilot trigger-add <autopilot-id> \
  --kind schedule --cron "0 9 * * 1" --timezone Asia/Shanghai \
  --output json

# 3. 确认状态
multica autopilot get <autopilot-id> --output json
```

用 `--mode create_issue`（而不是 `run_only`）：巡检的产出必须留下痕迹，否则「这周查过了没有要改的」这个信息就没有地方承载。

建议频率 **两周一次**。AI 领域一周内的真正新概念通常不到 2 个，每周跑大半是空转；间隔超过一个月，积压的候选又会多到一次读不完。

跑起来之后要偶尔看一眼 `multica autopilot runs <autopilot-id> --output json`：`LAST_STATUS=failed` 的巡检等于没跑，但表面上看不出来。

## 6. 边界：巡检不改内容

巡检**绝不**直接改 `content/`，也不直接发 PR。原因是第 3 节第三关的那个判断——「不懂它会不会让人做错决定」——是**判断**，不是规则。把它交给一个自动任务直接落库，图谱的筛选标准会在几轮之内悄悄退化。

正确的手工链路是：

```
巡检 issue（建议清单）
   └─▶ 人工/Mika 勾选要做的
        └─▶ 一个内容 PR 任务（按 CONTRIBUTING.md 走）
             └─▶ 三层测试 + 发布
```

巡检的职责到「清单」为止。它把「发现」这件事自动化了，把「判断」留给人——这个分工是有意的。

## 7. 一次巡检做不到什么

写清楚，免得下次有人对结果期望错位：

- **不保证覆盖**。它扫的是公开源，扫不到闭门讨论、内部文档、还没公开的工作。
- **不判断对错**。它提「这个新概念值得进图谱」，不保证聚类、前置关系一定挂得对——那是写 PR 时的事。
- **不追热点**。热点是它的输入，不是它的输出。一份全是上周热点的清单，说明第三关没认真过。
- **不替代人读**。它是筛选器，不是权威。清单上的每条都可能在 PR 阶段被否掉，这是正常的。
