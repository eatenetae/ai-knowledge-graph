## 场景背景

一家券商的零售业务线要做合规问答助手：客户经理在向客户推荐基金前，要查产品能不能卖、卖给这类客户有没有限制、话术里哪些词不能说。现在靠翻内部合规手册和问合规部门，平均一个问题等半天。（以下数字为虚构但典型的场景。）

立项时市场上有五个候选：两家头部厂商的云端 API、两个可私有化部署的开源模型、还有一个供应商提议的「通用模型 + 合规语料微调」方案。合规部的要求只有一句话：**答案错一次的代价，比答案慢一千次的代价都大。**

## 决策点

1. **怎么算「赢」**：五个候选同台比什么？直接看公开榜单的分数行不行？
2. **准确性之外还有什么硬约束**：数据能不能出公司？每千次问答的成本差多少？
3. **POC 做到什么程度算数**：演示好看就选，还是有一套能服众（包括合规部）的流程？

## 决策过程

**先定评测集，再谈模型。** 团队第一周没碰任何模型，而是拉着合规部从三处出题：历史咨询记录里挑高频问题、合规手册的边界条款改写成提问、让资深合规员出「容易答错」的陷阱题。题目分两层——有标准答案的（能不能卖、限额多少）自动比对；开放咨询类的（这类客户该注意什么）由合规员人工打分。总共三百多题，每题标注了出处条款。**判断依据：公开榜单量的是通用能力，我们的场景要的是「在合规知识上的准确率」，两者不能互相代替。**

**POC 设计成盲测。** 五个候选统一接入同一套检索（合规手册建知识库，答案必须附条款出处），同一批题目跑三轮，报告只报编号不报厂商，避免「大厂光环」先入为主。微调方案单独加测：除了准确率，还看它改一次知识要多久——合规政策一个季度能变好几回，**知识更新靠重新微调的方案，在这条硬约束下天然吃亏**。

**成本按业务口径折算，不按单价。** 不是比「每百万 token 多少钱」，而是算「一个客户经理每月问两百次，五种方案各花多少、私有化的机器和运维折进去是多少」。折完发现便宜模型答简单题、贵模型答难题的分级组合，比全用任何一个单一候选都划算——但这建立在评测把题目难度分层了的基础上。

**输出格式作为验收项。** 要求每个答案以固定结构给出（结论 / 依据条款 / 原文位置），因为下游要嵌进客户经理的工作台做引用跳转。结构稳定性的差距，成了最后两个候选之间的胜负手。

## 结果与教训

三周 POC 后选定「云端 API 主力 + 私有化小模型兜底敏感数据」的组合，盲测准确率比最强的单一候选高，成本处于中游（虚构但典型的数字）。上线后每季度用同一套评测集回归一次。

教训：

1. **POC 的核心交付物不是「选了谁」，是「怎么算赢」的共识。** 评测集先于模型存在，选型才不是吵架。
2. **榜单分数是入场券不是答案。** 通用能力都够用的今天，差距在你的题目上，不在他们的榜上。
3. **把「知识多久更新一次」当一等公民。** 它直接决定 RAG 和微调谁是主力——这条判断比任何单次测评结果都值钱。

## 面试怎么讲

一句话开场：金融场景选模型，难点不在「哪个模型强」，在「怎么设计一场让合规部门都认账的比拼」。重点讲两个判断：为什么公开榜单不可信（量错东西）、为什么把知识更新频率放进硬约束（它淘汰了微调主力方案）。收尾讲结构：评测集三百题、盲测三轮、成本按业务口径折算。如果被问「为什么不干脆全用最强的」，答「准确性达标后，成本和更新速度才是长期变量」——这句话就是这道题的加分位。
