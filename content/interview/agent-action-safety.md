## 好答案的要点

- **按后果分级，而不是按功能罗列**：只读类（查询、汇总）可自主；生成类（草稿、建议）产出默认不直接生效；**对外副作用类（发送、支付、删除、修改共享状态）必须用户当次确认，且确认界面展示完整内容**。「读」和「写」的权限要分开——最危险的事故都是「读的权限被借去写了」。
- **知道 Agent 的独有风险面**：它读的每一份外部内容（邮件、网页、文档）里都可能藏着冒充你指令的文字（提示注入），而 Agent 恰恰会照着执行。所以「给它的工具」本身要最小化——不需要删除权限就别配，权限清单是安全边界的第一道墙。
- **不确定性的笼子**：模糊决策（要不要这么改）给模型，确定性执行（怎么改、改多少）给传统系统；钱和对外动作永远经过人的确认或硬性规则。
- **可回滚、可审计**：动作有日志、有操作主体、出问题能撤回——「能撤销」和「能追责」是设计目标，不是运维补丁。

## 常见的错误答案

- 「提示词里写清楚不许做危险操作」——用礼貌用语当门锁；提示注入恰恰是绕过这句话的攻击。
- 「我们内部系统，不用考虑这些」——内部数据被外发、被批量修改，同样是事故。
- 只有「加确认、加确认」，说不出分级标准和为什么读/写要分开——框架是背的。

## 追问

- 「用户抱怨每步都要确认太烦，怎么平衡？」（考察分级运营：按用户历史与动作风险动态调整确认粒度，数据推着自动化走。）
- 「一个只读的 Agent 也需要安全设计吗？」（考察：读本身可被注入利用去「复述」敏感内容到草稿里——读的权限也能变成写的出口。）
